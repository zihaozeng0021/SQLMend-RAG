# SQLMendRAG knowledge base pipeline

This directory is the knowledge base construction module of SQLMendRAG: grab the official information of five databases, clean, supplement metadata, remove duplication, and cut into pieces, and finally get `corpus.jsonl` that can be directly used for BM25 or vector indexing.

The paths such as `data/`, `config/`, `reports/` in this article are relative to `construction/`. Project-level descriptions are in the previous level [README](../README.md). New indexing, retrieval, generation or annotation modules should not be stuffed into the data stage of this directory.

## Why choose these five databases?

We only cover PostgreSQL, MySQL Community Edition, SQLite, MariaDB, and DuckDB. The reasons are very practical: they are common or growing rapidly, can be installed for free, project information is public, and can be easily reproduced in the laboratory. PostgreSQL, SQLite, MariaDB, and DuckDB themselves are all open projects; MySQL is limited to the Community Edition and gives priority to its public GPL source code.

## What’s in the warehouse now?

```text
construction/
  data/
    raw/{postgresql,mysql,sqlite,mariadb,duckdb}/ # Original text + Collect metadata
    interim/ # Parsing, cleaning, and deduplication intermediate products
    processed/
      corpus.jsonl # Production corpus: structure-aware chunking
      corpus_fixed.jsonl # Fixed length experimental baseline
  scripts/{collect,parse,clean,deduplicate,enrich_metadata,chunk,validate,statistics}/
  sqlmend_pipeline/ # Testable and reusable core code
  config/sources.yaml # Source, version, license, fixed hash
  config/chunking.yaml # Chunking, deduplication, balancing, acceptance threshold
  reports/ # Statistics, coverage, failure records, verification results
  tests/
```

Each JSON in `data/raw` retains the original text, original headers, source URL, UTC crawl time, dialect, version, source type, local path, content SHA-256 and character encoding information. The original compressed package is placed in the `.archives/` directory of the corresponding dialect. When re-running at a breakpoint, it will be hashed a priori and then reused.

By the way, Git boundaries: `raw`, `interim`, download archives and fixed-length baselines can all be regenerated by commands, so they are not tracked by default; the production `corpus.jsonl`, configuration, code, statistics, coverage, verification results and 100 audit samples will be retained. The raw/intermediate products in the workspace will not be deleted.

## Data sources and licensing instructions

The complete machine-readable listing is at [config/sources.yaml](config/sources.yaml). Each source clearly states `authority_class` to distinguish community articles from official information.

| System | Primary Sources | Versioning | Source Levels/Licensing Points |
|---|---|---|---|
| PostgreSQL | HTML or SGML manual in the official release archive | 18.6, 17.11, 14.24 reserved separately | Official project documentation; copyright and disclaimer reserved in the PostgreSQL Documentation License |
| MySQL Community | Official `mysql/mysql-server` HELP table and error directory in fixed submission | 8.4.0–8.4.11, 8.0.0–8.0.46 | Project maintenance technical documentation, source file is GPLv2 |
| SQLite | 3.53.4 static HTML package released by the official website | The current manual is 3.53.4; historical versions are extracted from the release log title | Official project documents; SQLite states that its code and documents belong to the public domain |
| MariaDB | Official document repository fixed submission, add 11.4.10 HELP/error directory | Universal page label `current`; release notes extract 10.x/11.x precise version; structure directory label 11.4.10 | Official/project maintenance information; record CC BY-SA / GNU FDL or GPLv2 page by page, exclude "all rights reserved" pages |
| DuckDB | Official `duckdb-web` fixed submission of current manual and release articles | Current manual notes 1.5 series; release articles extract precise versions | Official project/release documents; warehouse uses MIT License |

There is an easy pitfall here: Although Oracle's MySQL online manual is authoritative, it is not GPL, and the terms have restrictions on modification and independent redistribution. Therefore, the releasable corpus uses only the HELP and error information included in the official Community source code tree by default. They still have canonical URLs corresponding to manuals, are solid enough in SQL syntax, functions, operators and error retrieval, and do not hide authorization risks.

All remote bales are pinned to releases or commits and have official SHA-256, official SHA3-256, or archived SHA-256 after first validation in the manifest. The scraper does not bypass logins, paywalls, robots, rate limits or other access controls. SQLite directly uses the document ZIP provided by the official website and does not crawl the Fossil `/src` and `/docsrc` paths that it prohibits crawling.

## Finished in one run

Requires Python 3.10 or above. It is recommended to create a virtual environment first:

```powershell
cd construction
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e ".[test]"
python -m sqlmend_pipeline.cli build
```

For Linux/macOS, just replace the activation command with:

```bash
source .venv/bin/activate
```

If you have installed it from the project root directory using `python -m pip install -e ".\construction[test]"`, you can also run the CLI directly from the root directory; it will automatically recognize `construction/`. For full explicit control of the path, use `python -m sqlmend_pipeline.cli --root construction build`.

`build` will sequentially collect, parse, clean, supplement metadata, document deduplication, chunking, generate statistics and verify. Any hard acceptance failure will eventually return a non-zero exit code. It is safe to rerun: if the URL corresponding to the file and the content hash are consistent, it will be reused directly. The old file will not be appended to the end, and the half-downloaded file will not be regarded as a successful file.

If you just want to reuse the downloaded original text, you can run:

```powershell
python -m sqlmend_pipeline.cli build --skip-collect
```

## Run and troubleshoot in stages

```powershell
python -m sqlmend_pipeline.cli collect

```

You can also replenish only a certain source:

```powershell
python -m sqlmend_pipeline.cli collect --source sqlite_3_53_4_docs
```

If downloading fails, see `reports/collection_report.json` and `reports/download_failures.jsonl`; if parsing fails, see `reports/parse_report.json` and `reports/parse_failures.jsonl`. There are currently no failed or inaccessible sources for the complete collection of fixed snapshots, and the report will faithfully change when network or upstream status changes in the future.

## What exactly did cleaning do?

The parser processes HTML, Markdown, XML/SGML and plain text respectively, and also separately understands MySQL/MariaDB's `fill_help_tables.sql` and error message directory. The latter two types of files appear to be one or two large files, but are actually restored to HELP topics or error records, retaining numerical error numbers, symbol names, SQLSTATE, placeholders such as `%s`/`%d`, explanations, examples and canonical URLs.

Cleaning will remove navigation, footers, cookie hints, duplicate directories, PostgreSQL's Prev/Up/Home/Next page tables, GitBook/Marketo controls, Liquid display tags, and license footers, but the license information will be left in the metadata. Crossreference pages automatically generated by SQLite and used only for site construction are not candidates for production. SQL code, command line examples, configuration snippets, error strings, function signatures, operators, and case are not "polished" away. The table will become searchable like this:

```text
Table:
- SQLSTATE: 23505 | Condition: unique_violation
```

In other words, the relationship between the column name and each value is still there, and there will not be just a string of cells separated from the table header.

## Chunking strategy

The production corpus uses structure-aware chunking: Document → Chapter → Sub-Chapter → Explanation/Grammar/Examples. The default target is 150 words, the main text is at least 35, the normal maximum is 260, and the overlap is 20. The parameters are all in [config/chunking.yaml](config/chunking.yaml). The minimum length is based on the main text and will not rely on long synthetic headers; short signatures, parameters, return values, error records, and code/tables are still retained as meaningful atomic chunks. Adjacent sections are paired to avoid splitting function signatures and parameters. Overlapping content will be clearly marked as `Context carried from the preceding passage`, and no separate half-sentence tail block will be generated. Code blocks will be tied to the immediate explanation; error messages will not be separated from error numbers; tables will just be cut between rows, retaining column names in each sub-block. Individual blocks of code that are extremely long but must be preserved intact are allowed to exceed the normal maximum and will be faithfully reflected in the statistics.

For future ablation experiments, the pipeline will also generate a fixed-size baseline `data/processed/corpus_fixed.jsonl` of 180 words and 30 words of overlap. Production indexes should use `corpus.jsonl` and do not mix the two sets.

`chunk_id` is determined by document ID, policy, chapter position and text hash; the same input and configuration will result in the same ID. `Title` and `Section` are added at the beginning of each block, so that the context can be understood without leaving the entire original text.

## How to record version and metadata

Only record information that is explicitly supported by the source:

- Use `exact` to publish packages accurately;
- To explicitly override a version family use `range`;
- For official current documents but no reliable patch number, use `current`;
- Use `legacy` to clarify the old version;
- Only use `unknown` when you really can't judge.

The release notes of SQLite, MariaDB, and DuckDB will be further refined from version titles to chunks; identical or similar text across versions will only be merged if the version range is the same and has no independent semantics.

The produced JSONL contains at least the following fields:

```json
{
  "chunk_id": "smr_postgresql_...",
  "document_id": "doc_postgresql_...",
  "dialect": "postgresql",
  "vendor_or_project": "PostgreSQL Global Development Group",
  "version": "18.6",
  "version_min": "18.6",
  "version_max": "18.6",
  "version_status": "exact",
  "source_type": "official_docs",
  "source_name": "PostgreSQL 18.6 Reference Manual",
  "source_url": "https://...",
  "title": "SELECT",
  "section": "SELECT > Examples",
  "text": "...",
  "contains_sql": true,
  "contains_error_code": false,
  "retrieved_at": "2026-08-27T...Z",
  "content_hash": "..."
}
```

In addition, `source_id`, `authority_class`, `topic`, `chunking_strategy` and version/compatibility prompt flags are retained to facilitate future filtering and experiments.

## Deduplication and balancing

Exact deduplication uses SHA-256 after normalizing whitespace. Approximate deduplication first uses deterministic 64-bit SimHash to find candidates, and then calculates the Jaccard of normalized 5-word shingles. The default similarity threshold is 0.94. The rules are intentionally conservative: only compare within the same dialect and version range; keep error symbol sets if they are different; cross-dialect or meaningful cross-version content will not be merged. What has been deleted and how similar it is are written into `document_duplicate_report.json` and `chunk_duplicate_report.json`.

The size of the candidate documents varies greatly, so it is not a simple "accept all" in the end. Targeting 2,400 blocks per dialect, polling first between topics such as Syntax, Functions, Errors, Migrations, Types, Transactions, Configuration, Release Notes, and then between Sources, Source Types, and Versions. In this way, a very large official website will not be filled with corpus, nor will release notes with hundreds of version titles crowd out grammatical and error information. The hard rules are still at least 1,000 per side, no more than 35% for either side, and at least 10,000 total.

## Reporting, Validation and Testing

The statistics command will automatically write:

- `reports/corpus_statistics.json`
- `reports/corpus_statistics.md`
- `reports/source_coverage.csv`
- `reports/version_coverage.csv`
- `reports/inspection_sample.jsonl` (fixed random seed, five-party stratified drawing of 100 blocks)
- `reports/manual_inspection.json` (manual itemized results, sample/corpus SHA-256 and boundary observations)

The validation command will write each PASS/FAIL, observation value, requirement, failure reason and repair suggestion to `reports/validation_report.json`. It checks for JSONL, IDs, required fields, URLs, five-party vocabularies, version status, encoding, short garbage, exact/near duplicates, count vs. word count, dialect ratio, version coverage, source manifest consistency, checkable samples, and suspected credentials in files to be tracked.

Run the test:

```powershell
python -m pytest
```

Tests cover four types of parsers, metadata extraction, dialect normalization, version parsing, two types of deduplication, cross-version protection, structural/fixed chunking, code block protection, table transformations, navigation cleanup, stable IDs, statistics, source manifest consistency, and validation failures that must return a non-zero status.

## Known limitations

- MySQL does not collect the entire online manual and release notes separately authorized by Oracle by default, so the release note coverage is weaker than that of the other four parties; this is a clear licensing trade-off, not a hiding of deficiencies.
- DuckDB does not have a centralized numerical error code table like PostgreSQL, and mainly retains official error categories and original messages such as Binder, Catalog, Parser, and Conversion.
- MariaDB's current document version prompts are scattered. Common pages that cannot be reliably determined are only marked with `current`, and the exact version will not be randomly filled in. Mixed permission pages are filtered page by page, excluding 145 pages that are not allowed to be reused in this snapshot.
- PostgreSQL 17/18 releases provide structured SGML instead of generated HTML; the source URLs for these passages point to verifiable official archive members, and for 14.24 they point directly to versioned web pages.
- Currently, only the current manual and the complete historical release log of SQLite are retained. There is no copying of multiple highly similar old manuals in the entire package.
- Automatic consistency checking cannot replace legal advice, nor can it replace manual error analysis in the final paper. `inspection_sample.jsonl` is the entrance reserved for manual inspection.
- Haven't done BM25, vector indexing, retrievers or RAG generators yet, this is intentionally left for later stages.
